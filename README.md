# Voter & Membership System — Phase 1

A straightforward PHP, MySQL, Bootstrap and AdminLTE application.

## Run on Laragon

Start Apache and MySQL in Laragon, then open the `APP_URL` configured in `.env` (currently `http://localhost/ndcvotermember`). Sign in with your existing administrator email and password.

The previous database was backed up and reset at your request. It now contains the Phase 1 schema only. No voter, member or upload records were seeded. The administrator login was retained; previous sessions were invalidated.

## Phase 1 workflow

### Reusable residential towns

Residential Region, District and Town selectors have search inside each dropdown using locally stored Tom Select 2.4.3. Type a town name to search saved towns within the selected residential region/district. The Add town action appears only when no case/accent-insensitive partial match exists. New names are saved only with the voter. Popular-town tags show up to 12 towns in the selected district, ranked and sized by their current linked voter counts; no district means no tags. Unused towns remain searchable. Changing a parent clears dependent selections. Assets are local; no new migration is required.

Manually check Add/Edit voter in Laragon: select a residential region and district, click a popular-town tag, switch districts and confirm that the old town clears and tags refresh. Search for an existing town, then a name without matches and choose Add town. Save and reopen to confirm the selection. Check editing an existing voter, blank town and read-only access. Native saved-town selections remain available if enhancement fails; adding a new name requires JavaScript. Database checks/imports remain manual in phpMyAdmin.

After migrations 09 and 10, import the complete **database/12_residential_towns_mysql8.sql** in phpMyAdmin. It creates the `residential_towns` directory, adds the voter town reference and links town names already present in your records. The migration can resume/repeat without resetting data and adds no sample towns.

When saving a voter, choose their residential region/district if known, then select a suggested town or type a new one. The app normalizes surrounding/repeated whitespace and creates or reuses a dictionary entry for that name within the selected residential region/district. Duplicate names in that scope are prevented; the same name in different districts is separate. Towns without region/district are still allowed and stored in an unassigned scope. A failed save or rolled-back CSV upload creates no town entries. Clearing/changing a voter town updates the voter link but retains the old dictionary entry for later reuse. Correctly spelled town names are important: different spellings remain separate entries.

The Town input offers matching saved names for the current residential region/district. **Residential towns** lists saved towns, region/district, voter counts and links to matching Voters/Members. Both people lists offer **Saved residential town** for exact town filtering, alongside the existing town-text search. Region/district changes refresh the saved-town options; filters persist across pagination. CSV address saves use the same dictionary automatically. No extra town setup step is required beyond saving a voter. Before migration 12, the old town-text field continues to save normally.

Manual checks: save your own voter with a new town and confirm it appears in Residential towns and later suggestions. Save another voter in the same location using different capitalization/extra spaces; verify it reuses one entry. Repeat the same name in another district and verify a separate entry. Check no-region/no-district duplicates, changing/clearing a voter town, exact filters, text search and pagination. Reject an invalid voter/CSV and confirm no new towns remain. Use **database/phpmyadmin_town_checks.sql** for read-only duplicate, linkage and count checks.

Unknown values stay blank; **No formal education** is an explicit value, different from unknown. Use consistent profession/skill names and commas between multiple skills/languages. ### Optional voter photos

In phpMyAdmin, select the application database and import **database/06_voter_photos_mysql8.sql** once. Existing voters are unchanged and no photos or sample records are added. Before the migration, voter forms continue working without photos and show setup guidance.

On **Add voter** or **Edit voter**, optionally select a JPEG, PNG or WebP image, then **Save voter**. Files must be up to 2 MB, at most 6000 pixels per side and at most 12 megapixels. PHP GD is needed for upload processing (enabled in the checked Laragon PHP installation). A preview appears before saving. Replace a photo by selecting another file, or check **Remove current photo when saving**. Leaving the upload blank preserves the current photo. If validation fails, select the upload again before retrying.

The application corrects JPEG orientation where available, resizes images to a maximum of 1024 pixels per side, and re-encodes them to JPEG without EXIF/GPS metadata. Images are stored privately in `voter_photos`; only authenticated staff can retrieve them through the application. Photo changes and voter edits are committed together and audited. Voter and member profiles display the same photo; without one, they show an initials placeholder. CSV updates and membership removal preserve photos. Include `voter_photos` when backing up the database.

Manual checks: add your own voter without a photo; add a valid image, replace it, save with no new file, and remove it. Confirm profiles match and removal clears both. Try an unsupported image, an oversized file, and an invalid voter form with a replacement photo; existing details/photo must remain unchanged on failure. Check CSV updates and removing membership keep the photo. Confirm the photo URL requires sign-in. Database checks are in **database/phpmyadmin_photo_checks.sql** and exclude image contents.

1. **Upload voters**: download the empty CSV template, fill in your own data and upload it. `voter_id`, `first_name` and `last_name` are required in the new template; legacy full-name layouts are also accepted. Location, contact details, gender and birth date are optional. There are no source, edition or review prerequisites.
2. **Voters**: search, add and edit voter records. Location is optional; choose entries from the Locations directory.

To undo membership, open the member profile and choose **Remove membership**, then confirm. Administrators and registration officers can use this action. The voter record, contact information and polling station stay intact; the person disappears from Members and appears under Voters → Not members. Keep voter IDs as text to preserve leading zeros. Dates use YYYY-MM-DD. Gender accepts unknown, female, male or other (M/F are also accepted).

Contact details remain encrypted using the existing `.env` application key. Passwords remain hashed, and forms use CSRF protection. Staff roles are Administrator, Registration officer and Read-only staff; this phase retains only your existing administrator account.

## One person, one editing workflow

Once enrolled, their member profile becomes the editing point for all personal details, photo, contact information, residential address, electoral location, membership and background. Nothing imports automatically. Correct/re-upload the file, or tick the explicit exclusion checkbox to skip ALL duplicate, invalid and conflicting rows and confirm the remainder. A file containing only problems cannot be confirmed. All-skipped reviews may be finished to record their skipped totals.
